# 项目实施计划

## 一、我们准备做什么

本项目计划开发一个帮助用户核查图文新闻的小系统。用户提供一段新闻文字和一张图片，系统尝试找到外部材料，判断这些材料是否可靠、是否真的与新闻有关，再给出核验结果和理由。

第一版的目标是让**一条新闻从输入到生成核验报告的过程能够完整运行**，而不是先做复杂的网页界面。新闻平台接入、自动封禁新闻和训练大型模型不属于这次开发范围。

## 二、开始写代码前，先确定这些事情

| 需要先商量的事情 | 为什么要先确定 | 建议由谁准备 |
|---|---|---|
| 用什么语言开发、怎样运行程序 | 否则两个人写的代码可能无法放到一起运行 | 瓦峻昊提出方案，两人确定 |
| 用什么方式搜索新闻资料和图片 | 可能涉及账号、接口限制或费用 | 栾健调研，两人确定 |
| 使用哪些新闻和图片作测试 | 要确保样本能使用、能重复测试 | 栾健整理，两人确定 |
| 一条新闻有多项事实时，如何给总体结果 | 需要统一判断办法，不能让 AI 每次临时决定 | 瓦峻昊组织讨论 |
| 每次运行最多花多少钱、调用多少次接口 | 避免产生无法控制的费用 | 两人共同确定 |
| 是否正式采用 ADR 中提出的证据检查方案 | 目前是待验证的方案，不能直接当成已证明有效 | 两人共同评审 |

## 三、整个项目分几步完成

| 阶段 | 这一阶段做什么 | 做完后要看到什么 |
|---|---|---|
| 第 0 步：准备 | 选定开发工具、测试办法、分工和费用范围 | 两人确认后续能够开始开发 |
| 第 1 步：程序能启动 | 完成输入新闻和图片的基本程序，并提取新闻中的待核实内容 | 能运行示例，并能提示错误输入 |
| 第 2 步：能够找资料 | 获取文字证据和图片来源线索 | 能查看找到的材料及出处 |
| 第 3 步：能够给出核验结果 | 检查证据质量、形成判断、生成报告 | 可以看到结论、依据和不足之处 |
| 第 4 步：提高稳定性 | 完善报错、日志、安全检查和费用限制 | 出现故障时有记录，能定位问题 |
| 第 5 步：统一验收 | 完成规定测试，比较改进前后的表现，整理交付文档 | 组员可以按说明重新运行、检查结果 |

**任务先后关系：** 先让程序能启动，再做新闻内容提取；文字检索和图片核查可以在输入格式确定后分别开发；证据质量检查完成后才能稳定生成核验报告；最后再做完整测试。基础日志应从第一阶段就开始记录，不必全部留到最后。

## 四、具体开发任务和两人分工

任务编号 `TASK-01` 至 `TASK-08` 只是方便管理的代号。

| 任务 | 要做的事情 | 建议负责人 | 人工复核人 |
|---|---|---|---|
| TASK-01 | 搭建能够启动的程序，接收新闻文字和图片 | 瓦峻昊 | 栾健 |
| TASK-02 | 从新闻中找出需要核实的事实，并做好编号 | 栾健 | 瓦峻昊 |
| TASK-03 | 搜索相关新闻文字资料，记录资料来源 | 瓦峻昊 | 栾健 |
| TASK-04 | 查找图片来源，并检查图片与新闻是否匹配 | 栾健 | 瓦峻昊 |
| TASK-05 | 检查证据是否可靠、相关、独立和足够 | 瓦峻昊 | 栾健 |
| TASK-06 | 根据证据生成判断结果和核验报告 | 栾健 | 瓦峻昊 |
| TASK-07 | 增加报错提示、安全保护、运行日志和费用限制 | 瓦峻昊 | 栾健 |
| TASK-08 | 测试整个系统、比较改进效果并整理交付材料 | 栾健 | 瓦峻昊 |

每个任务的具体做法和检查要求见 `tasks/` 文件夹中的对应任务卡。

## 五、一个开发任务怎么开始、怎么算完成、出问题怎么办

### 5.1 开始开发前，要确认什么

1. **知道要做什么：** 例如“让程序能够读取一张图片并检查文件是否有效”，而不是笼统地说“完善图片模块”。
2. **知道谁负责：** 明确负责开发的人、负责人工复核的人，以及哪个 AI 写代码、哪个 AI 负责复审。
3. **知道改哪些内容：** 确认本次可以修改的文件，以及不应该顺便修改的其他功能。
4. **知道怎么判断做对了：** 提前准备至少一个正常示例和一个错误示例，并说明预期结果。
5. **知道能用什么：** 如果需要新软件包、收费接口或外部数据，先经两人确认。

如果这些问题还没有答案，先把问题补充清楚，再正式开发；不必为了赶进度让 AI 猜测。

### 5.2 什么情况下，任务才算完成

一个任务必须同时满足以下条件，才能标为“已完成”：

1. 代码或文档已经实际完成，并且没有擅自增加任务范围以外的功能。
2. **真正运行过** 约定的检查或测试，结果符合预期；没有运行过的测试只能写“未测试”。
3. 开发过程中已经让**另一个 AI 分阶段复审**，发现的问题有处理记录。
4. 另一位组员完成了人工检查，同意合并本次修改。
5. 保存 Git 提交记录、主要测试结果、还没解决的问题，并更新相关说明。

**例子：**“图片输入功能”能读取正常图片，遇到损坏图片能提示错误；两个例子都实际测试过，另一个 AI 检查过代码，另一名组员也确认了，这才叫完成。

### 5.3 开发时出了问题怎么办

| 情况 | 应该怎么做 |
|---|---|
| 普通代码错误，例如运行时报错 | 记录错误信息，修改代码，重新测试 |
| 想新增收费服务、改变重要规则、超出原定修改范围 | 先向两名组员说明，再决定要不要做 |
| 发现密钥泄露、严重安全问题，或测试一直失败却找不到原因 | 先停止相关修改和操作，保存错误记录，请组员一起判断 |
| 新代码导致原来正常的功能不能运行 | 撤销有问题的修改，必要时恢复到此前**确实测试通过** 的版本，再重新检查 |

**不要把“AI 说已经修好了”当作修复成功。** 必须重新运行相关测试。找不到稳定版本时，应说明目前无法恢复，不能写“回退成功”。

## 六、两个 AI 怎么配合，两个人怎样确认

本项目计划使用**AI-A 编写代码，AI-B 独立检查代码**。两个 AI 尽量使用不同模型或独立会话，避免第二个 AI 只重复第一个 AI 的结论。

1. **写代码前：** AI-A 先提出开发计划，AI-B 检查计划有没有明显遗漏。
2. **写完一个小功能后：** AI-A 提交本阶段代码和测试结果，AI-B 检查是否有错误、安全隐患或遗漏的测试。AI-A 修改后再交给 AI-B 复查。
3. **准备合并时：** AI-B 再检查整体改动、测试结果和未解决的问题。
4. **最后由人确认：** 瓦峻昊写的代码由栾健复核；栾健写的代码由瓦峻昊复核。双方共同决定重大风险操作。

每次复审至少留下：任务编号、检查的代码版本、发现的问题、修改情况和最终复核人。**AI 之间互相同意，不等于程序已经通过真实测试。**

## 七、开发中可能遇到的主要问题

| 可能的问题 | 打算的处理办法 |
|---|---|
| 程序还不能启动 | 先完成 TASK-01，尽早建立可运行的基本程序 |
| 搜索服务不稳定或者太贵 | 先用保存好的测试结果调试；正式联网前设置次数和费用限制 |
| 找不到图片的原始来源 | 记录“暂时无法确认”，不编造图片出处 |
| 证据检查太宽松或太严格 | 用有明确依据的测试案例比较两种错误，逐步调整 |
| 两个 AI 都没有发现同一个错误 | 保留实际运行测试，由另一名组员人工复核 |
| 开发时间不足 | 优先完成完整的基本流程，暂时放下不重要的展示功能 |
| 改动导致旧功能出错 | 保存修改记录，重新测试，必要时恢复稳定版本 |

## 八、怎样知道项目真的完成了

不能只看“代码写完没有”，还要看测试结果。《规约》里已有 **19 项要求（`FC-01` 至 `FC-19`）** 和 **12 个测试场景（`T-01` 至 `T-12`）**。这些编号只是方便找到对应内容，不需要记住每个缩写。

`acceptance-matrix.md` 是一张**检查对照表**，用于记录：某项要求由哪个任务实现、用哪个案例测试、测试是否实际通过，以及结果保存在什么地方。

测试记录至少写清楚：测试了什么、用了什么数据、预期会发生什么、实际发生什么、是否通过、对应的代码版本。测试失败或者暂时无法执行，都应照实填写。

另外，TASK-08 要比较**启用与不启用新增证据质量检查机制** 时的核验表现。重点看错误判断有没有减少、有效证据有没有被误排除，以及运行时间和费用是否合理。两种实验条件尽量保持一致，不能只挑成功的例子展示。上述比较仅在受控测试中进行，不代表允许在正式使用时忽略安全底线。

## 九、最后准备交付哪些材料

1. 能实际运行的项目代码，以及安装、启动和测试说明。
2. 八张任务卡及每项任务的完成记录。
3. 全部规定测试的结果，包括未通过和未执行的项目。
4. 两个 AI 的阶段复审记录，以及两名组员的人工复核记录。
5. 核验报告示例、运行日志、实验对比结果和对应代码版本。
6. 更新后的 README、项目计划与验收检查对照表。

提交前，应让**没有负责该部分代码的另一名组员** 按说明重新运行关键流程，确保不是只有开发者自己的电脑能够运行。
